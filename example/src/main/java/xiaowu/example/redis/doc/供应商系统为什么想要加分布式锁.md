# SupplierPullSchedulingApplicationService - 供应商系统为什么想要加分布式锁

### Current goal

这一步先不写代码，我们把业务场景讲清楚：**为什么供应商调度适合用 watchdog 分布式锁，而且为什么应该加在 `SupplierPullSchedulingApplicationService.scheduleDueConnections()` 这一层。**

理解这个点很关键。否则你只会“会用 Redisson”，但面试或技术评审时说不清楚为什么这么设计。

### Why this step exists

这个业务叫“供应商拉取调度”。

它不是直接去供应商 ERP 拉数据，而是做一轮扫描和派发：

```text
扫描到期的 supplier_connection
        |
尝试给每个供应商连接抢 DB lease
        |
抢到 lease 后发布 Kafka 拉取任务
        |
worker 后续异步拉取 ERP 数据
```

也就是说，这个 service 是一个 **调度器**，不是 worker。

它的职责是：

```text
找出现在应该被拉取的供应商连接，并把任务派发出去。
```

### Under the hood

你现在的调用链有两个入口：

```text
定时任务入口：
SupplierPullSchedulingJob.scanAndDispatch()
        |
        v
SupplierPullSchedulingApplicationService.scheduleDueConnections()

手动触发入口：
SupplierSchedulingController.dispatchOnce()
        |
        v
SupplierPullSchedulingApplicationService.scheduleDueConnections()
```

所以 `scheduleDueConnections()` 是共同业务入口。

如果我们把锁加在 `SupplierPullSchedulingJob`：

```text
定时任务会被锁住
手动接口不会被锁住
```

这样手动触发仍然能和定时任务撞车。

如果我们把锁加在 Controller：

```text
手动接口会被锁住
定时任务不会被锁住
```

也不完整。

所以最合理的位置是：

```text
SupplierPullSchedulingApplicationService.scheduleDueConnections()
```

因为两个入口最终都会走这里。

---

这个场景里有两种“并发风险”。

第一种：多个应用实例同时跑定时任务。

比如你部署了 3 个实例：

```text
app-1: @Scheduled 触发 scanAndDispatch()
app-2: @Scheduled 触发 scanAndDispatch()
app-3: @Scheduled 触发 scanAndDispatch()
```

Spring 的 `@Scheduled` 是每个 JVM 自己触发一次。它不会天然知道别的机器也在跑。

所以同一时间可能出现：

```text
3 个实例同时扫描 supplier_connection
3 个实例同时查到差不多的一批候选连接
3 个实例同时尝试抢 DB lease
```

虽然 DB lease 最终能挡住重复派发，但系统会出现很多无效竞争。

第二种：手动触发和定时触发撞车。

比如：

```text
10:00:00 定时任务触发
10:00:01 运维人员在 Swagger 点了手动 dispatch
```

如果没有外层锁，它们会同时进入 `scheduleDueConnections()`。

---

那为什么已有 DB lease 还要加 Redisson 锁？

因为它们保护的粒度不同。

DB lease 现在是在每个 supplier 上抢：

```java
supplierConnectionRepository.tryAcquireLease(
    connection.getSupplierId(),
    connection.getVersion(),
    now,
    leaseUntil,
    now);
```

它保护的是：

```text
同一个 supplier 不要被重复派发
```

Redisson watchdog 锁保护的是：

```text
整轮调度扫描不要并发执行
```

可以这样理解：

```text
Redisson watchdog lock = 外层闸门
DB lease = 每个供应商任务自己的安全扣
```

没有 Redisson 锁，DB lease 仍然可以保证大部分正确性，但会有问题：

```text
重复扫描数据库
重复抢同一批 supplier 的 lease
产生大量 version 冲突
增加数据库压力
日志更乱
调度结果不可预测
```

有了 Redisson 锁之后：

```text
同一时间只有一个实例做整轮扫描
其他实例快速失败或跳过
DB lease 继续兜底单个 supplier 的并发安全
```

这就是“减少竞争 + 保留兜底”的设计。

---

为什么这里适合 watchdog，而不是固定 `leaseTime`？

因为调度扫描的执行时间不稳定。

它可能受这些因素影响：

```text
本轮 batchSize 变大
数据库慢查询
Kafka publish 卡顿
网络抖动
GC pause
下游 Kafka broker 短暂不可用
```

如果用固定租约，例如 5 秒：

```text
实例 A 拿到锁
实例 A 执行超过 5 秒
锁自动过期
实例 B 拿到锁
实例 A 和 B 同时跑调度
```

这正是我们不想看到的。

watchdog 的语义更适合：

```text
只要实例 A 还活着，并且业务还没执行完，Redisson 自动续期
实例 A 执行完后 finally unlock
如果实例 A 崩溃，续期停止，锁最终自动过期
```

所以 watchdog 适合：

```text
执行时间不稳定，但同一时间只允许一个实例执行的后台任务
```

这就是供应商调度的典型场景。

---

为什么不加在更底层，比如 Repository？

Repository 只负责数据库访问，它不知道业务含义。

如果在 Repository 加锁，会变成：

```text
findSchedulableConnections 加锁？
tryAcquireLease 加锁？
publish Kafka 又怎么办？
```

锁的范围会被切碎，保护不了完整业务流程。

这里真正需要互斥的是：

```text
扫描候选连接 -> 抢 DB lease -> 发布 Kafka task
```

这是一段完整业务流程，所以锁应该放在 Application Service。

### Now edit this

这一步不用改代码。你只需要记住这个设计结论：

```text
watchdog 分布式锁加在 SupplierPullSchedulingApplicationService.scheduleDueConnections()
```

它保护的是：

```text
整轮供应商调度扫描和派发
```

不是保护：

```text
单个 supplier 的 lease
```

单个 supplier 的安全仍然由 DB lease 负责。

### Checkpoint

你可以用这句话检查自己是否理解：

```text
Redisson watchdog 锁防止多个实例同时跑整轮调度；
DB lease 防止同一个供应商连接被重复派发。
```

如果你能把这句话说清楚，就理解了这个设计。

### Common mistake

1. 以为有 DB lease 就完全不需要外层锁。实际上 DB lease 保证正确性，但不减少整轮调度竞争。
2. 把锁加到 `SupplierPullSchedulingJob`。这样手动触发入口绕过锁。
3. 把锁加到 Controller。这样定时任务入口绕过锁。
4. 用固定 leaseTime 保护长耗时调度。任务超时后锁会过期，可能出现并发执行。
