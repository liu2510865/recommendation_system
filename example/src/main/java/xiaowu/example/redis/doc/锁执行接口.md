# DistributedLockExecutor - 锁执行接口

### Current Goal

这一步先定义一个“锁执行器接口”，不直接写 Redisson 代码。

目标是让业务层以后只关心“我要在锁内执行这段逻辑”，而不是到处写 `redissonClient.getLock()`、`tryLock()`、`unlock()`。

### Why This Step Exists

你这个项目已经有比较清晰的端口风格，比如：

- `ReservationCacheGateway`
- `ReservationEventPublisher`
- `ReservationEventPublisher`

所以分布式锁也应该先定义成 application 层的能力边界。

这样做的好处是：业务代码不直接依赖 Redisson。以后如果你想换成数据库锁、ZooKeeper、Redis Lua 锁，业务服务不用大改，只换实现类。

### Under The Hood

分布式锁本质上是一个“临界区保护器”。

普通写法是：

```java
lock.lock();
try {
    // business logic
} finally {
    lock.unlock();
}
```

但我们不希望业务层每次都重复这套模板，所以把它封装成：

```java
lockExecutor.executeWithLock(..., () -> {
    // business logic
});
```

运行时流程会变成：

1. 调用方传入锁 key、等待时间、租约时间、业务逻辑。
2. 实现类尝试获取锁。
3. 拿到锁才执行业务逻辑。
4. finally 中释放锁。
5. 没拿到锁就抛出业务异常或返回失败。

### Now Edit This

新建文件：

`C:\Users\admin\Desktop\recommendation_system\example\src\main\java\xiaowu\example\payment\seckill\application\port\DistributedLockExecutor.java`

写入这个接口：

```java
package xiaowu.example.payment.seckill.application.port;

import java.time.Duration;
import java.util.function.Supplier;

public interface DistributedLockExecutor {

  <T> T executeWithLock(
      String lockKey,
      Duration waitTime,
      Duration leaseTime,
      Supplier<T> action);
}
```

先只写这一个方法。

参数含义：

- `lockKey`：锁的 Redis key，比如 `lock:seckill:sku:1001`
- `waitTime`：最多等多久去抢锁
- `leaseTime`：拿到锁后多久自动释放
- `action`：真正要保护的业务逻辑

### Common Mistake

1. 文件路径要放在 `application\port`，不是 `infrastructure\redis`。
2. `Supplier<T>` 适合有返回值的业务逻辑；先不要加 `Runnable` 重载，避免一开始接口变复杂。
3. `leaseTime` 不要理解成等待时间，它是“拿到锁以后，锁最多持有多久”。
